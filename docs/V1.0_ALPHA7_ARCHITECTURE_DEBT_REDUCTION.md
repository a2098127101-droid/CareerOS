# CareerOS v1.0-alpha7 · Architecture Debt Reduction & Configurable Engines

## Goal

Alpha7 addresses architecture debt identified after alpha6 instead of adding another layer of unrelated UI. It focuses on four concrete problems:

1. schema ownership was split across Alembic, migration code and Store-local DDL;
2. workflow/artifact behavior retained fixed career-development assumptions;
3. Structured Jobs lacked a production-domain match engine;
4. Evidence verification did not preserve a durable AI→human decision history.

## Delivered

### Centralized schema ownership

SQLite Store modules no longer create their own tables/indexes. The SQLite compatibility runtime materializes the checked-in SQLAlchemy metadata in the central migration layer and then applies forward compatibility/data migrations. PostgreSQL continues to use Alembic.

This does **not** mean SQLite CRUD has been removed. Legacy SQLite repositories intentionally remain for local/offline compatibility and are listed by `scripts/audit_database_access.py`.

Target architecture:

```text
Router → Service → Repository Contract
                  ├─ SQLite compatibility repository
                  └─ SQLAlchemy/PostgreSQL repository

Schema ownership:
SQLite      → centralized migration layer / checked-in metadata
PostgreSQL  → Alembic
```

### Workflow templates

Workflow runtime is now selected using the tenant product preset. Built-ins include:

- career_development_v1 — 10 stages
- campus_career_v1 — 10 stages
- career_service_v1 — 7 stages
- career_competition_v1 — 10 stages
- enterprise_talent_v1 — 7 stages

Every stage may declare required Evidence and/or required Artifact metadata. Existing default behavior is preserved for legacy sessions.

### Artifact templates

Artifact type resolution is canonicalized. Legacy labels such as `简历`, `职业规划书` and `PPT` map to canonical kinds without hard-limiting the request model to only those three values.

The current alpha7 engine is a **built-in template foundation**. Tenant-authored template CRUD and arbitrary renderer execution remain a later phase.

### Job Intelligence

The engine decomposes structured job data into explicit requirements, stores those requirements, and compares them against participant profile/evidence independently.

Important safety rule:

> A job requiring Python does not imply the participant knows Python.

Statuses:

- MATCHED
- PARTIAL
- MISSING
- UNKNOWN

Each result exposes requirement, evidence, reason, confidence and recommended action.

### Evidence verification history

Verification is no longer only a mutable status on a Claim. Every update can create an immutable history entry containing:

- previous_status
- new_status
- confidence
- verifier_type (`ai` or `human`)
- verified_by
- reason
- timestamp

Advisor/organization-admin manual verification can override the active status while retaining the AI decision history.

### Router modularization

Privacy and commercial/analytics routes were extracted from `main.py` into router factories with unchanged URLs. This is deliberately incremental to minimize breaking changes. `main.py` is still large and further domain-router extraction remains technical debt.

## Explicit non-claims

Alpha7 does **not** claim:

- live PostgreSQL certification;
- live pgvector search;
- live Redis multi-instance correctness;
- live S3/R2/MinIO round-trip;
- live semantic embedding;
- live LLM end-to-end Agent chain;
- true NLI/LLM entailment verification;
- tenant-authored arbitrary workflow/artifact template CRUD;
- real billing or SSO;
- 100/500/1000 concurrency capacity.

Those remain Runtime/Beta blockers.
