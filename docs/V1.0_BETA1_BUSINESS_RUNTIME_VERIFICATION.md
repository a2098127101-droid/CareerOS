# CareerOS v1.0-beta1 · Business Runtime Verification Candidate

## Release intent

beta1 does not add another layer of showcase-only features. It upgrades the release gate from **component connectivity** to **business-runtime evidence**.

A production-like deployment must now be able to prove both:

1. infrastructure dependencies work together; and
2. the real CareerOS business path works through authentication, tenant isolation, Agents, private files, artifacts and Evidence verification.

## Added verification layers

### Runtime certificate

The existing signed runtime certificate covers:

- PostgreSQL Repository certification,
- pgvector capability,
- Redis,
- distributed rate-limit state,
- independent Redis worker completion,
- expired-worker-lease recovery,
- private S3-compatible object round-trip,
- real semantic embedding call,
- at least one real generation provider,
- external observability sink health endpoint.

A PASS is not granted from configuration alone.

### Business E2E certificate

A separate signed certificate exercises the running HTTP application:

```text
Authenticated participant
→ Session
→ Profile Agent
→ Coach
→ private file upload
→ Writer / Artifact V1
→ Reviewer
→ Evidence verification
→ Critic + Revision / Artifact V2
→ Artifact trace
→ cross-tenant attack attempts
→ LLM usage proof
```

The gate additionally verifies a semantic RAG quality fixture with current/old/conflicting sources and cross-tenant retrieval isolation.

Certification identities use unique random credentials and are de-identified/archived during cleanup. Known default certification credentials are prohibited.

## Migration and recovery

beta1 adds two non-destructive staging drills:

- realistic SQLite fixture → snapshot → temporary PostgreSQL database → Alembic → import → verification → Repository read-back;
- temporary PostgreSQL schema → `pg_dump` → drop → `pg_restore` → marker integrity read-back.

Neither drill touches the primary application database beyond creating/dropping disposable certification resources.

## Worker verification

The runtime certifier never executes the probe job itself. A separately running worker must consume and complete it. A second check creates an expired RUNNING lease, requires recovery to QUEUED, then requires an independent worker to finish it.

This is materially stronger than a Redis `PING`, but it is still not a full chaos-engineering campaign.

## Object storage verification

A storage PASS requires:

```text
PUT
→ SDK GET / SHA256
→ presigned URL
→ real HTTP GET / SHA256
→ DELETE
```

Generating a signed URL without fetching it is not sufficient.

## Load gate

The beta1 staging gate runs a small measured HTTP smoke/load test by default. This validates the harness and produces P50/P95/P99/error data for the staging endpoint.

It is **not** evidence of 100/500/1000 concurrent AI capacity. Those scenarios still require a dedicated live capacity campaign with real PostgreSQL, Redis, workers, RAG and model traffic.

## Current status

The build environment used to produce this package does not expose Docker, a live PostgreSQL/pgvector service, Redis, MinIO/S3, semantic embedding credentials or a generation-model credential.

Therefore:

- implementation and local regression: VERIFIED;
- live staging runtime certification: NOT VERIFIED;
- business runtime certification: NOT VERIFIED;
- commercial production readiness: NOT CLAIMED.

The intended next milestone is **v1.0-beta1 Runtime Verified** only after the staging gate produces valid signed Runtime and Business certificates and all migration/recovery/load gates pass on real infrastructure.
